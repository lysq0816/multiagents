# 电商售后多智能体 MVP 开发计划

## 1. 项目目标

在 10 个工作日内交付一个可本地运行、可量化评测的售后工单系统，验证难度路由多智能体在复杂工单上是否比单智能体更可靠。

MVP 仅处理：

1. 未发货订单取消；
2. 已收货商品退货；
3. 已收货商品换货。

补发、语音客服、真实电商平台接入、自动资金操作和模型微调不进入首版。

## 2. 最终交付物

- 单智能体基线；
- 固定多智能体基线；
- 难度路由多智能体工作流；
- 独立审核和人工确认节点；
- τ-bench Retail 评测适配器；
- 轻量工单与审批界面；
- 实验结果、成本统计和演示脚本；
- Docker 化本地部署说明。

## 3. 工作流

```text
用户工单
  -> 受理与结构化
  -> 难度路由
      -> 普通工单：客服智能体
      -> 复杂工单：订单智能体 + 政策智能体
  -> 方案汇总
  -> 独立审核
  -> 查询自动执行 / 写操作人工确认
  -> 状态校验
  -> 用户回复
```

工具执行器是确定性程序，不是 LLM 智能体。所有写操作必须同时满足业务前置条件、用户确认和审核通过。

## 4. 难度路由规则

以下任一条件成立即视为复杂工单：

- 同时包含多个业务意图；
- 涉及多个订单；
- 一次需要执行多个写操作；
- 业务政策存在冲突或例外；
- 同时涉及资金和库存变化。

信息缺失时先进入澄清流程，不启动无意义的多智能体讨论。

## 6. 评测指标

- 任务完成率；
- 最终数据库状态正确率；
- 政策违反率；
- 未授权写操作数；
- 人工转接率；
- 工具调用次数；
- 响应延迟；
- token 与模型成本；
- 多次运行一致性。

关键指标使用数据库状态和确定性规则评测，不以 LLM 自评作为唯一依据。

## 7. 验收门槛

- 100% 写操作具有用户确认和审计记录；
- 100% 政策判断具有可定位来源；
- 0 个不可追踪的业务状态变化；
- 至少完成 30 个核心任务，每个任务重复 3 次；
- 复杂任务相较单智能体满足以下至少一项：
  - 成功率提高 10 个百分点；
  - 政策违规率下降 30%；
- 平均模型调用成本不超过单智能体的 2 倍。

## 8. 风险控制

- 所有业务工具首先运行在沙箱；
- 不记录 API Key 和完整支付信息；
- 智能体不得绕过身份验证；
- 写操作必须幂等；
- 审核失败不得自动重试写操作；
- 智能体之间只传递最小必要信息；
- 模型失效时可回退到人工客服。
